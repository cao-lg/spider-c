上一章结尾留了一句话：「会写爬虫是本事，知道什么时候不爬是修养。」这一章就把"什么时候不爬、为什么"讲透。

先看一个真实场景：某同学写了个很干净的爬虫，遵守 robots、控制了频率、只抓公开列表页，技术上挑不出毛病。他把数据整理后卖给了一家做竞品分析的公司——半年后收到律师函，理由是"未经授权抓取并商业使用平台数据，构成不正当竞争"。他很不理解："我又没破解、没高并发，数据还是公开的啊。"

这正是本章要解决的问题：**技术可行、法律允许、道德正当，是三道独立的关**。过了一道，不代表过了另外两道。

> **为什么单独讲伦理？** 很多从业者翻车，不是技术不够，而是不知道自己已经越过红线。第 11 章把 robots.txt 放在"反爬四层"的合规层里点到为止；这一章不重复反爬技术，专门讲法律与伦理这条底线。

## 一、三道关：技术 / 法律 / 伦理

| 关口 | 问的问题 | 判断依据 | 典型误区 |
| --- | --- | --- | --- |
| 技术可行 | 我能不能抓到？ | 请求、解析、渲染能力 | "抓得到就够了" |
| 法律允许 | 我有没有权利抓、用？ | 法律法规、服务条款、授权 | "公开的就是免费的" |
| 道德正当 | 这样做会不会伤害别人？ | 对服务器、对用户、对生态的影响 | "别人都在抓" |

三者的关系是**递进且不可互相替代**的：技术能力只是入场券。一个爬虫可以在技术上完美无缺，同时在法律和伦理上完全站不住脚。

专业工程师的价值，恰恰体现在能主动停在"能做但不该做"的地方。这不是怯懦，而是对数据、对用户、对自己负责。技术本身中立，但**使用技术的人有边界**。

## 二、robots.txt：君子协定，不是技术屏障

绝大多数站点根目录有 `/robots.txt`，用简单的文本声明哪些路径允许或禁止抓取。课程靶站的文件就是这样写的：

```
User-agent: *
Disallow: /private/
Disallow: /admin/
```

含义是：对所有爬虫（`*`），`/private/` 和 `/admin/` 两个目录不欢迎来访。Python 标准库 `RobotFileParser` 能程序化判断——不用装任何第三方库，课程运行器里也能跑：

> `can_fetch` 返回 True 只代表站方没禁止，不代表数据可随意使用。

### 关于 robots.txt 的两个常见误解

| 误解 | 事实 |
| --- | --- |
| 「写了 Disallow 就抓不到」 | 服务器根本不会读 robots.txt。本站 `/private/` 被 Disallow，却依然返回 200 —— 禁止是**站长的请求**，执行靠抓取方自觉 |
| 「没被 Disallow 就能随便用」 | robots 只回答「能不能来」，不回答「能不能用」。著作权、个人信息、用户协议是另外几道关 |

本站的 `/robots.txt` 就是现成的教材：靶站 `/practice/` 没有被列出，所以默认可抓；`Disallow: /private/` 和 `Disallow: /admin/` 划出两处禁区。你若真的去请求 `/private/`，会拿到一个正常 200 的页面——那一页讲的就是这件事本身。**服务器返回 200，恰恰证明 robots.txt 是声明不是屏障**：它靠的是抓取方的自觉，而不是技术拦截。

### 其他常见指令速查

| 指令 | 含义 | 爬虫该怎么办 |
| --- | --- | --- |
| `User-agent: *` | 适用于所有爬虫 | 通用规则，优先级低于指定名字的组 |
| `User-agent: MyBot` | 只针对特定名字的爬虫 | 你的 UA 含该名字时，优先遵守这一组 |
| `Disallow: /admin/` | 禁止抓取该路径及其子路径 | 直接跳过，别抱侥幸 |
| `Allow: /public/` | 显式允许，与更宽泛的 Disallow 配合 | 注意实现差异，用 `can_fetch` 实测 |
| `Crawl-delay: 10` | 站方建议的请求间隔秒数 | 非标准字段，按它设 `sleep` 下限更礼貌 |
| `Sitemap: https://.../sitemap.xml` | 告诉爬虫站点地图在哪 | 优先从 sitemap 取 URL，少瞎爬 |

> `Crawl-delay` 不是 RFC 正式字段，各库支持不一；`RobotFileParser` 提供 `crawl_delay()` 读取它，返回空值时你得自己定一个礼貌的间隔。

> **三个真实的坑(本站 robots.txt 就是照这三条写的)**
>
> 1. **规则文件保持纯 ASCII。** `.txt` 响应通常不带 charset，`requests` 按 ISO-8859-1 解码，
>    中文注释全变乱码；更糟的是 `str.splitlines()` 会把乱码字节里的 `0x85`(NEL)当成换行，
>    规则被切碎，`can_fetch` 于是对**所有**路径都返回 True。中文说明写网页里，别写进规则文件。
> 2. **别写多余的 `Allow: /`。** 「没被 Disallow 就是允许」，这行不增加信息；实测它在
>    Python 3.14 里会让 `can_fetch("/private/")` 翻回 True(3.13 为 False)——同一份规则，
>    不同版本判出相反结论。写得越少，踩坑越少。
> 3. **规则要紧跟 `User-agent`。** 组内插一个空行或一行注释，有些实现就认为这组结束了，
>    后面的 `Disallow` 变成孤儿规则、被静默忽略。
>
> 这三条不是理论，而是本课判题能跑通的前提。真实世界里各家解析器实现不一，
> **别假设某个库一定对**——用 `can_fetch` 实测。

## 三、真实案例：越界往往就差几步

法律风险的积累，往往不是某一步特别恶劣，而是几步小错叠加。

### 案例 1：公开数据 + 商业转售 = 不正当竞争

开头那位同学的场景不是个例。司法实践里有大量类似纠纷：一方投入多年成本积累平台数据，另一方抓取后做"实质替代"——用别人的数据直接分流其用户、攫取其商业机会，即便数据是公开的，也常被认定构成不正当竞争。**关键点在于"实质性替代 + 损害他人利益"，而不是"技术上有没有破解"。**

### 案例 2：以为只是"抓了点用户名"

某招聘站爬虫批量抓取简历上的姓名、手机号、邮箱并入库，本想"做人才分析"。这些字段全部属于个人信息，手机号更是典型敏感信息。批量收集、存储他人个人信息，即便没有转卖，也可能触犯侵犯公民个人信息相关的法律责任。**"我没有用来干坏事"不是辩解理由，非法获取本身就是问题。**

### 案例 3：高并发把服务器打挂

某同学爬一个 500 页的站点，开了几十个线程无间隔请求，站点数据库被拖到响应缓慢、正常用户无法访问。这不是"效率优化"，而是可能触犯破坏计算机信息系统相关规定的行为。**爬虫的并发数，本质上是在给别人家的服务器做压力测试——你没有这个权利。**

> 这三个案例的共同点：技术上都不难，甚至"很规范"。翻车的不是代码，是**对边界的判断**。

## 四、法律法规框架：核心是"别乱抓、别乱用"

不必背法条编号，重点是理解每部法律关心什么、对爬虫意味着什么：

| 法律 / 规范 | 关注点 | 对爬虫的启示 |
| --- | --- | --- |
| 《网络安全法》 | 网络运行安全，不得危害网络安全、非法侵入他人网络 | 别用技术手段突破防护，别干扰系统正常运行 |
| 《数据安全法》 | 数据分级分类保护，重要数据受重点保护 | 金融、地图、人口等重要数据别乱抓乱存 |
| 《个人信息保护法》 | 处理的合法基础、最小必要、知情同意 | 能不碰个人信息就不碰，确需处理要有合法依据 |
| 《著作权法》 | 作品表达受保护，数据库汇编也可能受保护 | 抓来原文再发布、商用，有侵权风险 |
| 刑法相关规定 | 非法侵入 / 破坏计算机信息系统罪等 | 绕过技术措施、高并发致瘫，可能触及刑事风险 |

三部与数据最相关法律的侧重点可以这样记：**网络安全法管"别搞坏系统"，数据安全法管"别乱动重要数据"，个人信息保护法管"别乱碰人的信息"**。著作权与刑法则是另外两道独立的高压线。

> 具体条款解释请以官方文本和专业法律意见为准。本课程只讲原则性的风险认知，不做法律意见。

## 五、个人信息：界定与处理原则

这是最高频的踩雷区，先把"什么算个人信息"讲清楚：

| 维度 | 说明 | 实践做法 |
| --- | --- | --- |
| 什么是个人信息 | 以电子或其他方式记录的、能单独或结合其他信息识别特定自然人的各种信息 | 姓名、手机号、邮箱、身份证号、账号、精准位置、设备标识都算 |
| 敏感个人信息 | 一旦泄露或滥用更易危害人身财产安全、损害人格尊严 | 生物识别、医疗健康、金融账户、行踪轨迹、未成年人信息——原则上不碰 |
| 合法基础 | 处理个人信息需要合法性依据（如同意、履行合同所必需等） | 爬公开网页通常不构成合法基础，别默认"公开即可处理" |
| 最小必要 | 只处理实现目的所必需的信息，不得超范围 | 列表页够用就别去详情页带出用户字段 |
| 目的限定 | 收集时声明的目的，后续不得随意变更用途 | 用"学习研究"名义抓来转售，是典型越界 |
| 脱敏 / 去标识化 | 去掉或替换能识别到个人的字段 | 入库前手机号中间四位打码、删掉用户名与邮箱 |

一个实用判断法：**如果这条数据能对应到一个具体的人，就当个人信息处理；如果拿不准，就当敏感信息处理，或者直接不抓。**

## 六、三档红线与授权层级

把行为按风险分成三档，一眼看清边界：

| 行为 | 定位 | 判断要点 |
| --- | --- | --- |
| 遵守 robots、控频、抓公开且非个人的数据，仅自用学习 | 合规 | 声明范围内 + 无负载 + 用途正当 |
| 有开放 API 就用 API | 合规（推荐） | 最稳、最快、最体面 |
| 抓登录后自己有权访问的数据 | 高风险 | 看条款；不得用他人账号、不得绕过权限 |
| 用 UA / Referer 伪装突破明确的访问控制 | 高风险 | 可能违反条款，情节严重触及法律 |
| 复制他人平台数据做实质性替代、分流其用户 | 高风险 → 违法 | 司法实践中常认定不正当竞争 |
| 抓取个人信息并存储、交易 | 违法红线 | 侵犯公民个人信息相关法律责任 |
| 破解验证码、绕过付费墙等技术保护措施 | 违法红线 | 可能违反条款乃至刑事风险 |
| 高并发把服务器打挂 | 违法红线 | 可能构成破坏计算机信息系统 |
| 抓取后二次转售数据 | 违法红线 | 超出授权目的，侵犯数据权益 |

再看数据使用的**授权层级**，这决定了"抓来之后能怎么用"：

| 层级 | 数据来源 | 能否用于项目 |
| --- | --- | --- |
| 1 公有领域 / 开放许可 | 明确声明可自由使用（如 CC0、公开课教学沙盒） | 可以，注意署名要求 |
| 2 官方开放 API | 站方主动提供、带使用条款 | 可以，遵守 API 条款与配额 |
| 3 公开网页但无明确授权 | 人人可看，但未声明可抓取 / 商用 | 谨慎：自用学习通常可接受，商用需评估 |
| 4 登录后可见 | 需账户，受用户协议约束 | 仅限自己有权访问的范围，别批量导出 |
| 5 付费 / 受技术保护 | 付费墙、会员专享、验证码 | 不碰，除非获得明确授权 |
| 6 个人信息 | 任何可识别自然人的数据 | 原则上不抓；确需处理须有合法基础并脱敏 |

## 七、抓取前自查清单

爬之前问自己七个问题：

- [ ] 我有没有先看 `robots.txt`？尊重 Disallow。
- [ ] 我的 `User-Agent` 是否包含可联系信息？（如 `MyBot/1.0 (contact@example.com)`）
- [ ] 我是否控制了频率，不打垮服务器？
- [ ] 我是否避开了个人信息和重要数据？
- [ ] 我的数据是否仅用于学习 / 授权用途？
- [ ] 我有没有读服务条款（ToS），确认没有禁止自动化抓取？
- [ ] 有没有官方 API 可以替代自己爬？

### 频率与服务器负载

- 控制 `time.sleep` 间隔，别打挂站点；被限流时读 `Retry-After` 退避（第 11 章已讲）。
- 避开高峰期（网站运营期间、用户活跃时段）。
- 只抓必要字段，不拖数据。

> **频率控制的道德准则**：曾有新闻站点因爬虫长时间高并发请求导致服务器过载、服务中断数小时。这不是段子——爬垮别人的服务器可能承担法律责任。控制频率不是"技术选项"，是底线。

### 服务条款（ToS）

ToS（Terms of Service）是你与站点之间的合同。很多站点在其中明确写了"禁止使用机器人、爬虫、抓取工具访问"。你注册时点了"同意"，就受它约束。**不读 ToS 就开爬，相当于没看合同就签字。** 它是独立于 robots.txt 的另一道关：robots 没禁，不代表 ToS 允许。

### 合规要求的技术落点

| 合规要求 | 技术实现 |
| --- | --- |
| 检查 robots.txt | `RobotFileParser` + `can_fetch()` |
| 带联系 UA | `headers={"User-Agent": "MyBot/1.0 (email@example.com)"}` |
| 控频 | `time.sleep()` + 退避 |
| 数据最小化 | 只抓必要字段 |
| 授权获取 | 申请 API 或使用公开数据 |

### 数据生命周期的五个阶段

合规不止发生在"抓取"那一刻，而是贯穿数据的整个生命周期：

| 阶段 | 风险点 | 合规动作 |
| --- | --- | --- |
| 采集 | 越权访问、抓到个人信息 | 查 robots 与 ToS、字段最小化、控频 |
| 存储 | 泄露、留存过久 | 加密 / 脱敏、限制访问、设保留期限 |
| 使用 | 超出声明目的 | 用途与授权一致，变更用途需重新评估 |
| 共享 / 转售 | 侵犯数据权益、不正当竞争 | 默认不共享；确需共享先取得明确授权 |
| 销毁 | 残留副本泄露 | 到期删除，连同备份与中间文件一起清理 |

> 很多人把"合规"理解为抓取前看一眼 robots.txt 就够了。真正的专业做法，是**在每个阶段都留下可追溯的决定**：为什么抓这些字段、存多久、谁能看、什么时候删。

## 八、著作权、数据库权益与学术伦理

- **著作权保护表达，不保护事实。** 图书的书名、价格、ISBN 是事实，通常不受著作权保护；但商品描述文案、评论正文、整篇文章是"表达"，原文抓来再发布或商用，有侵权风险。
- **数据库权益是另一道关。** 即便单条数据不受版权保护，投入大量成本整理的数据库整体，在不少法域有专门保护，或可主张不正当竞争。"每条都不侵权"不等于"整库拿走没事"。
- **学术 / 科研伦理。** 发表研究时注明数据来源、遵守站点条款、不公开可识别个人的原始数据、不把爬来的数据当成自己的成果；必要时对数据做去标识化。数据的"可复现"不等于"可公开"。

## 九、常见坑排查表

| 常见想法 | 问题在哪 | 正确做法 |
| --- | --- | --- |
| "能抓就能用" | `can_fetch` 为 True 只说明站方没禁止访问，不等于获得使用授权 | 再看 ToS、版权、个人信息、用途 |
| "就抓了点用户名" | 用户名、手机号、邮箱都算个人信息，批量抓取加存储有法律风险 | 只抓业务必需的非个人字段，必要时脱敏 |
| "我只是跳过付费墙看看" | 绕过技术保护措施可能违反条款乃至法律 | 不碰；需要就付费或申请授权 |
| "多开几个线程快点" | 高并发可能压垮服务器、触发法律责任 | 控频加退避，把 QPS 压在站点可承受范围 |
| "数据抓来转手卖掉" | 超出授权目的、侵犯数据权益，常构成不正当竞争 | 商用前先确认授权，别默认公开等于可卖 |
| "换个 UA 就能抓 /private/" | robots 禁区加 UA 伪装属于明知故犯 | 尊重 Disallow，别把伪装用在禁区 |

## 十、可运行练习：数据最小化与脱敏

合规不能只停在口号上，要落到代码里。下面这段用内置数据演示两个动作：**只保留必要字段**（最小化）和**给姓名打码**（脱敏）。全程标准库、无网络请求：

<CodeRunner
  variant="guided"
  title="抓取数据的脱敏与最小化"
  prompt="任务:records 是抓回来的用户记录。用标准库实现:1)只保留 name 和 city 两个字段(最小化) 2)把 name 中间字符用星号代替(脱敏)。打印处理后的结果。"
  code={`records = [
    {"name": "张小明", "phone": "13812345678", "city": "北京", "email": "zxm@example.com"},
    {"name": "李雷", "phone": "13987654321", "city": "上海", "email": "ll@example.com"},
]

def mask(name):

## 十一、小结

- **三道关**：技术可行 ≠ 法律允许 ≠ 道德正当，不能互相替代。
- **robots.txt 是声明，不是屏障**：能抓到 ≠ 被允许。`RobotFileParser` 只是帮你读懂声明。
- **法律框架**：《网络安全法》《数据安全法》《个人信息保护法》加著作权、刑法边界，核心是"别乱抓、别乱用"。
- **个人信息是最高压线**：界定要清楚，处理要遵循合法基础、最小必要、目的限定、脱敏。
- **三件实事**：抓取前过自查清单、控频不给服务器添负载、用途不越授权层级。
- **立场**：技术中立，但使用有边界。**会写爬虫是本事，知道什么时候不爬是修养。**

你写好了爬虫，请求发出去却收到 403；或者前 20 页好好的，第 21 页开始全是空页面。这不是代码写错了，而是网站**识别出你不是正常用户**。

反爬不是"攻防秀"，更不是"想办法绕过一切"。真正的专业做法是：**先判断被拦在哪一层，再在合规前提下让请求尽可能像一个正常用户**。这一章按难度分四层，每层配真实可复现的案例。

> **本章所有案例都可公开访问验证**：`httpbin.org` 是专门给开发者测试 HTTP 行为的公共服务，`quotes.toscrape.com`、`scrapethissite.com` 是公开声明供爬虫练习的沙盒。理解机制是为了写出更稳、更礼貌的爬虫，而不是攻击真实站点。

## 一、先诊断：你被拦在哪一层

遇到异常别急着改代码，先按状态码和网络面板定位：

| 症状 | 大概率原因 | 所在层 | 第一动作 |
| --- | --- | --- | --- |
| 403 Forbidden | UA / Referer / 缺失请求头 | 第一层：身份 | 补齐浏览器请求头 |
| 429 Too Many Requests | 请求太快 | 第二层：频率 | 降速 + 读 `Retry-After` |
| 返回 200 但内容是空壳 / 假数据 | 需要登录态、Cookie、JS 渲染 | 第二/三层 | 检查 Cookie 或回看第 10 章 |
| 偶尔成功、频繁失败 | IP 被限流、行为异常 | 第二/三层 | 控频 + 退避，必要时换出口 |
| 浏览器正常、脚本必挂 | TLS 指纹 / 浏览器指纹 | 第三层：指纹 | 考虑 Playwright（第 10 章） |

> **诊断顺序**：状态码 → 请求头对照 → 频率日志 → 是否需要登录 → 指纹。**80% 的问题在前两层就能解决**，别一上来就研究绕过验证码。

### 真实实验：用 httpbin 看服务器眼里的你

`https://httpbin.org/headers` 会把收到的请求头原样回显。先看看 `requests` 默认长什么样：

```python
import requests
r = requests.get("https://httpbin.org/headers", timeout=10)
print(r.json()["headers"])
# 你会看到 User-Agent 是 "python-requests/2.x" —— 等于举着牌子说"我是爬虫"
```

再加一组浏览器请求头对比：

```python
headers = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 "
                  "(KHTML, like Gecko) Chrome/126.0.0.0 Safari/537.36",
    "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
    "Accept-Language": "zh-CN,zh;q=0.9,en;q=0.8",
    "Accept-Encoding": "gzip, deflate, br",
}
r = requests.get("https://httpbin.org/headers", headers=headers, timeout=10)
print(r.json()["headers"]["User-Agent"])   # 已是浏览器样式
```

> 我实测过：`httpbin.org/headers` 会回显 `Accept`、`Accept-Language`、`Accept-Encoding`、`User-Agent` 等头。`httpbin.org/user-agent` 单独回显 UA，**改请求头前后一对比，效果一目了然**——这是调试反爬最好用的"镜子"。

## 二、第一层：身份伪装（UA 与请求头）

### 2.1 为什么默认 UA 会被拒

`requests` 的默认 UA 是 `python-requests/2.x`。许多站点的 WAF（Web 应用防火墙）会直接拦截这个特征。 mirrors 一个真实浏览器的请求头是基本功。

### 2.2 UA 不是"每次都换"

一个常见误区：每个请求都换 UA。真人浏览时 UA 在一整个会话里是**稳定的**——你用 Chrome 打开 10 个页面，UA 不会变。频繁跳变的 UA 反而像机器人。

**正确策略**：选定一个真实 UA → 整个会话保持不变 → 换会话时才换。

### 2.3 Referer：你从哪来的

有些站点检查 `Referer`（来源页）。比如图片服务器只允许"从本站页面点过来"的请求。直接访问图片 URL 会 403，带上正确的 Referer 就放行：

```python
headers = {
    "User-Agent": "Mozilla/5.0 ...",
    "Referer": "https://example.com/gallery/",   # 声明来源页
}
requests.get("https://example.com/images/1.jpg", headers=headers, timeout=10)
```

> **合规提示**：只在站点允许抓取的资源上这么做。伪造 Referer 绕过明确的访问控制，可能触及法律风险——见第 12 章。

## 三、第二层：行为控制（频率、退避、会话）

### 3.1 频率：256 次请求换来的教训

真实案例：某同学爬一个 500 页的图书站，用 `for` 循环无间隔请求，前 180 页顺利，第 181 页开始全部 403，IP 被封 24 小时。**原因就是请求间隔为 0**，模式比人快几百倍。

两个改进：

```python
import time, random

# 改进 1:固定延时(最简单)
time.sleep(1)

# 改进 2:随机延时(更像真人,推荐)
time.sleep(random.uniform(0.8, 2.2))

# 改进 3:每 20 页多歇一会儿,模拟人的浏览节奏
for page in range(1, 501):
    crawl(page)
    time.sleep(random.uniform(0.8, 2.2))
    if page % 20 == 0:
        time.sleep(random.uniform(3, 6))
```

> **延时不是越大越好**。慢到自己都嫌弃会降低采集效率。原则是"不给对方服务器压力"——如果站点 QPS 承受力是 10，你把频率控制在 1-2 就够礼貌了。

### 3.2 读懂 429 与 Retry-After

`429 Too Many Requests` 是服务器**明确告诉你"太快了"**的信号，很多响应头会带 `Retry-After`（建议等多久再试）。这是最应该被尊重的反爬提示。

我用 httpbin 实测过 `https://httpbin.org/status/429` 确实返回 429。处理范式：

```python
resp = requests.get(url, headers=headers, timeout=10)
if resp.status_code == 429:
    retry_after = resp.headers.get("Retry-After")
    wait = int(retry_after) if retry_after and retry_after.isdigit() else 60
    print(f"被限流,按服务器建议等待 {wait}s")
    time.sleep(wait)
```

### 3.3 指数退避 + 抖动：工业级重试

第 9 章讲过基础重试，这里给一个更完整的生产版本——加入**抖动（jitter）**防止多进程同时重试形成"惊群"：

```python
import random, time, requests

def fetch_with_backoff(url, headers, retries=4, cap=30):
    """指数退避 + 随机抖动;cap 限制最长等待,避免退避到天荒地老。"""
    for attempt in range(retries):
        try:
            r = requests.get(url, headers=headers, timeout=8)
            if r.status_code == 429:
                raise requests.exceptions.RetryError("限流 429")
            r.raise_for_status()
            return r
        except requests.exceptions.RequestException as e:
            if attempt == retries - 1:
                raise                       # 最后一次仍失败,抛出让上层处理
            base = min(cap, 2 ** attempt)    # 1, 2, 4, 8 ...
            wait = base + random.uniform(0, 0.5)   # 抖动
            print(f"第 {attempt+1} 次失败({e}),{wait:.1f}s 后重试")
            time.sleep(wait)
```

### 3.4 Session 维持登录态

很多站点登录后才能看数据。`requests.Session()` 会自动保存 Cookie，让后续请求带上登录态：

```python
session = requests.Session()
session.headers.update(headers)

# 第一步:登录(真实站点需按它的表单字段调整)
session.post("https://example.com/login",
             data={"username": "xxx", "password": "xxx"}, timeout=10)

# 第二步:登录后请求,自动带上 Cookie
r = session.get("https://example.com/dashboard", timeout=10)
```

> 注意：这里演示的是**你自己有权限访问的账户**。绕过他人账户、突破登录限制属于违规行为。

## 四、第三层：指纹识别（为什么 requests 终究露馅）

### 4.1 TLS 指纹：改请求头也没用

这是很多初学者困惑的终极问题：**"我把 UA、Referer、所有请求头都改成浏览器了，为什么还是被拦？"**

因为服务器不只看 HTTP 请求头，还看 **TLS 握手指纹**（俗称 JA3/JA4）。不同客户端（`requests` 用的 `urllib3`/OpenSSL 与 Chrome 用的 BoringSSL）在 TLS 握手时发出的参数组合不同，服务器能据此识别出"这是 Python 客户端"，**与你怎么改 UA 无关**。

| 识别维度 | requests 能否伪造 | 说明 |
| --- | --- | --- |
| User-Agent 等请求头 | ✅ 能 | 改 headers 即可 |
| Cookie / 登录态 | ✅ 能 | Session 维持 |
| TLS/JA3 指纹 | ❌ 基本不能 | 由底层 TLS 库决定 |
| Canvas / WebGL 指纹 | ❌ 不能 | 需要真实浏览器渲染 |
| 鼠标轨迹 / 点击行为 | ❌ 不能 | 需 Playwright 模拟或真实用户 |

> **结论**：当站点用了 TLS 指纹或浏览器指纹这类高阶手段，`requests` 无论怎么伪装都难以通过。这时正确的选择是回到第 10 章——**用 Playwright 驱动真实浏览器**，它的 TLS 栈和行为是真正由 Chrome 产生的。

### 4.2 验证码：识别它，而不是硬刚

验证码（图片、滑块、点选、无感）本质是"确认对面是人"。应对的正确姿势按优先级：

1. **避免触发**：控频、补全请求头、维持会话，让请求不像机器人——大多数验证码是被异常行为"惹出来"的。
2. **绕开需求**：找官方 API、数据是否能从别处合法获取。
3. **人工处理**：确需少量数据时，人工过一次验证码再继续。
4. **合规评估**：破解验证码可能违反站点条款乃至法律，**不要在课程里实现**。

> 课程立场：我们会讲清楚验证码**为什么存在、如何被触发**，但不会教你破解它。技术能力要用在正当场景。

## 五、第四层：合规是底线，不是可选项

反爬的另一面是"反反爬"的法律约束。**技术可行 ≠ 法律允许**。

### 5.1 robots.txt：君子协定

`robots.txt` 是站点对爬虫的**声明**。用 Python 标准库 `RobotFileParser` 就能读懂：

```python
from urllib.robotparser import RobotFileParser

rp = RobotFileParser()
rp.set_url("https://spider-c.pages.dev/robots.txt")
rp.read()   # 或 rp.parse(text.splitlines())

print(rp.can_fetch("Crawler", "https://spider-c.pages.dev/practice/level1-books/"))  # True
print(rp.can_fetch("Crawler", "https://spider-c.pages.dev/private/"))                # False
```

我们靶站的 `robots.txt` 明确规定 `Disallow: /private/`。**关键点**：`robots.txt` 只是声明，服务器对 `/private/` 依然返回 200——**遵守与否取决于爬虫作者，不是服务器强制**。这正是"君子协定"的含义。

### 5.2 真实红线清单

| 行为 | 是否可做 | 说明 |
| --- | --- | --- |
| 遵守 robots.txt、控制频率抓公开数据 | ✅ 通常可以 | 保持礼貌、不造成负载 |
| 用官方开放 API | ✅ 强烈推荐 | 最快最稳最体面 |
| 抓登录后自己有权访问的数据 | ⚠️ 看条款 | 不得绕过权限或使用他人账号 |
| 破解验证码、突破付费墙 | ❌ 不要做 | 可能违法、违反服务条款 |
| 抓取个人信息并存储/交易 | ❌ 违法 | 触犯个人信息保护相关法律 |
| 高并发压垮服务器 | ❌ 违法 | 可能构成破坏计算机信息系统 |

> 详见下一章「法律与伦理」。**记住：会写爬虫是本事，知道什么时候不爬是修养。**

## 六、代理 IP：理解原理，谨慎使用

代理让请求换个出口 IP，绕开 IP 级限流。原理简单：

```python
proxies = {
    "http": "http://user:pass@1.2.3.4:8080",
    "https": "http://user:pass@1.2.3.4:8080",
}
requests.get(url, headers=headers, proxies=proxies, timeout=10)
```

| 类型 | 成本 | 稳定性 | 风险 |
| --- | --- | --- | --- |
| 免费代理 | 免费 | 极差 | ⚠️ 可能窃听你的请求数据，不推荐 |
| 付费代理池 | 中 | 中-好 | 选正规服务商 |
| 住宅代理 | 高 | 好 | 价格高，合规风险也高 |

> **合规提醒**：代理的正当用途是**企业内网出口、合法的多地域测试**。用它来绕过明确封禁或大规模隐蔽抓取，风险自负。免费代理尤其危险——流量经过陌生服务器，账号密码可能泄露。

## 七、反爬应对总清单（排查速查）

| 现象 | 先检查 | 再处理 |
| --- | --- | --- |
| 403 | UA 是否 `python-requests` | 补浏览器请求头 + Referer |
| 429 | 请求频率、Retry-After | 降速 + 指数退避 + 抖动 |
| 空页面 | 是否需登录 / JS 渲染 | Session 登录态 / Playwright |
| 时好时坏 | IP 限流、行为异常 | 控频 + 稳定会话 |
| 脚本挂、浏览器正常 | TLS / 浏览器指纹 | 换 Playwright 真实浏览器 |
| 弹验证码 | 是否被异常行为触发 | 先降速、补请求头；不要硬刚 |

**四层递进策略**：

```
第一层 身份伪装  →  第二层 行为控制  →  第三层 指纹识别(上真实浏览器)
        ↓
第四层 全程合规(robots.txt / 条款 / 频率 / 数据用途)
```

## 八、小结

- **先诊断后动手**：按状态码和层次定位问题，80% 出在前两层。
- **第一层身份**：真实 UA + 完整请求头（用 `httpbin.org/headers` 验证），会话内保持稳定。
- **第二层行为**：随机延时 + 尊重 429/Retry-After + 指数退避抖动 + Session 维持登录态。
- **第三层指纹**：TLS/JA3、Canvas、行为轨迹 `requests` 伪造不了，这时用 Playwright。
- **第四层合规**：robots.txt 是声明不是屏障；破解验证码、抓个人信息、压垮服务器都是红线。
- **优先级**：能抓接口就别抓页面，能用官方 API 就别自己爬，能不做就不做。

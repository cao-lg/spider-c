爬虫本质上是**模拟浏览器发 HTTP 请求、读懂服务器返回的响应**。不懂 HTTP，你只会「抄代码」，一旦网站变卦就束手无策。这一章把 HTTP 讲透。

> 你可以把 HTTP 想象成「你和服务器之间的对话规则」。浏览器和服务器之间说的每一句话，都遵循 HTTP 协议。爬虫就是「旁听」这些对话，然后自己也开口说话。

> **本章的实验田**：我们会用 `httpbin.org`——一个专门给开发者测试 HTTP 行为的公共服务。它会把你发的请求「原样回显」给你，是理解 HTTP 最好用的镜子。这些案例**请用你本地的 Python 运行**（浏览器运行器受 CORS 限制，无法直连公网，原因见第 1 章第七节）。所有案例我都实测可用。

## 一、请求 / 响应模型

一次抓取就是一次对话：

```
你(客户端)  --请求 Request-->   服务器
你(客户端)  <--响应 Response--   服务器
```

请求里包含：要什么（URL）、用什么动作（方法）、附带什么信息（请求头/请求体）。
响应里包含：状态码（成不成功）、响应头（元信息）、以及真正的网页内容（HTML/JSON/图片）。

| 阶段 | 方向 | 你带什么 | 服务器回什么 |
| --- | --- | --- | --- |
| **请求 Request** | 客户端 → 服务器 | 请求行（方法+URL+协议）、请求头、请求体 | — |
| **响应 Response** | 服务器 → 客户端 | — | 状态行（状态码）、响应头、响应体 |

> 理解了这个「双向对话」模型，你读任何 HTTP 相关的报错（比如 403、429、timeout），都知道问题出在哪一边。

### 一次请求的「三要素」

浏览器 F12 → Network 里点开任意请求，你会看到它清楚地分成三块，这就是后面反复用到的**三要素**：

| 要素 | 内容 | 例子 |
| --- | --- | --- |
| ① 请求行 Request Line | 方法 + 路径 + 协议版本 | `GET /get?q=python HTTP/2` |
| ② 请求头 Request Headers | 一组键值对（你是谁、要什么） | `User-Agent: Mozilla/5.0 ...` |
| ③ 响应 Response | 状态行 + 响应头 + 响应体 | `HTTP/2 200 OK` + 头 + JSON |

记住这三要素，第三章学 `requests` 时你会发现：`requests.get(url, params=, headers=)` 正是在分别填充它们，而返回的 `resp` 正是把③交到你手上。

## 二、URL 结构拆解

URL 是爬虫的「目标地址」。一个完整的 URL：

```
https://books.example.com/search?q=python&page=2#top
|_____|   |__________________|  |____________|  |___|
  scheme     host + path          query         fragment
```

| 部分 | 含义 | 示例 |
| --- | --- | --- |
| `https` | 协议(scheme) | `http`（不安全）/ `https`（加密） |
| `books.example.com` | 主机(host) | 域名或 IP 地址 |
| `/search` | 路径(path) | 服务器上的资源路径 |
| `?q=python&page=2` | 查询参数(query) | `&` 分隔多个，`=` 键值对 |
| `#top` | 片段(fragment) | 浏览器内锚点，**不会发给服务器** |

> **注意**：`#` 后面的 fragment 只存在于浏览器本地（比如跳到页面某个锚点），服务器永远不会收到它。这也是为什么 URL 里改 `#` 后面的值不影响请求。

## 三、真实案例：把 httpbin.org 当 HTTP 实验室

光讲概念太抽象。下面三个实验，用你**本地 Python** 跑，亲眼看看 HTTP 到底传了什么。

### 3.1 实验一：`/get` 回显你的请求

`https://httpbin.org/get` 会把服务器收到的 GET 请求原样回显成 JSON：

```python
import requests

r = requests.get("https://httpbin.org/get", params={"q": "python", "page": 2}, timeout=10)
data = r.json()
print("状态码:", r.status_code)         # 200
print("查询参数:", data["args"])         # {'q': 'python', 'page': '2'}
print("我的出口 IP:", data["origin"])    # 形如 203.0.113.42
print("服务器看到的完整 URL:", data["url"])
```

**看到了吗**：你在 `params` 里传的参数，服务器通过 `args` 原样还了回来；`origin` 是服务器看到的你的公网出口 IP。这个接口是调试「参数到底传对没有」的利器——以后你自己写的请求拿不到数据，先拿它验证参数是否如你所想。

### 3.2 实验二：`/headers` 回显你的请求头

`https://httpbin.org/headers` 把收到的请求头原样返回：

```python
import requests

r = requests.get("https://httpbin.org/headers", timeout=10)
print(r.json()["headers"])
```

我实测时它返回了这些头（节选）：

```json
{
  "Accept": "*/*",
  "Accept-Encoding": "gzip, deflate",
  "Accept-Language": "*",
  "Host": "httpbin.org",
  "User-Agent": "python-requests/2.32.3"
}
```

> **关键发现**：`User-Agent` 是 `python-requests/2.32.3`——等于举着牌子告诉服务器「我是爬虫」。这就是为什么有些站点直接给你 403。改请求头前后各调一次 `/headers` 对比，是调试反爬最好用的「镜子」。第 3、11 章会深入这个话题。

### 3.3 实验三：`/status/418` —— HTTP 里的彩蛋

`https://httpbin.org/status/418` 会返回一个著名的彩蛋状态码：

```python
import requests

r = requests.get("https://httpbin.org/status/418", timeout=10)
print(r.status_code)   # 418
print(r.text)          # 一只 ASCII 艺术茶壶: "[ teapot ]"
```

> **顺手记住**：`httpbin.org/status/404`、`/status/500` 能让你故意制造错误响应，专门练习下一章要学的 `raise_for_status()` 和异常处理。把「主动制造错误」当成测试手段，是专业开发者的习惯——你不需要等网站真的挂掉才能验证自己的错误处理代码。

**418 I'm a teapot** 来自 1998 年愚人节的 RFC 2324「超文本咖啡壶控制协议」——规定「如果服务器是一台茶壶，收到煮咖啡的请求，应返回 418 拒绝」。后来它被正经收进 HTTP 状态码注册表的「玩笑保留」条目。它提醒我们：状态码是服务器给你的一段「语义信号」，不只是数字。

### 3.4 实验四：用 F12 观察一次真实请求的三要素

打开浏览器（Chrome / Edge），按 **F12** → 切到 **Network（网络）** 面板 → 访问 `https://httpbin.org/get` → 点开列表里那条 `get` 请求，你会看到：

1. **Headers（头）标签** → Request Headers 区：这里就是①请求行和②请求头。能看到 `Request URL`、`Request Method: GET`、`Status Code: 200`，以及 `User-Agent`、`Accept-Language` 等浏览器真实请求头。
2. **Response（响应）标签** → 这里是③响应体，正是实验一看到的那个 JSON。

> **专业习惯**：以后遇到任何「爬虫和浏览器表现不一致」的问题，第一动作就是 F12 把浏览器的真实请求抓下来，和你的 `requests` 请求逐项对比——差在哪个头、哪个参数，一目了然。**浏览器是最好的参考答案**。

## 四、方法：GET vs POST 对比

HTTP 方法（Verb）告诉服务器「你要做什么」。爬虫最常用 GET 和 POST：

| 维度 | GET | POST |
| --- | --- | --- |
| 用途 | 取数据（查列表、详情） | 提交数据（登录、搜索、下单） |
| 参数位置 | 拼在 URL 里（query string） | 放在请求体（body）里 |
| 可见性 | 可见，会留在历史/日志 | 不可见（相对） |
| 长度限制 | 有（URL 长度受限） | 理论上无限制 |
| 缓存 | 可被缓存、收藏 | 通常不缓存 |
| 安全性 | 不应传敏感信息 | 也不加密，但至少不进 URL |
| 爬虫场景 | 抓列表页、详情页（占 90%） | 登录、带复杂条件的搜索接口 |

> **核心区别一句话**：GET 的参数在 URL 里（看得见、有长度限制、可缓存），POST 的参数在请求体里（看不见、无长度限制、不可缓存）。大多数爬虫以 GET 为主，少数场景（登录、搜索）需要 POST。

## 五、状态码分类：服务器的一句话回应

状态码是三位数字，第一位决定类别：

| 范围 | 类别 | 含义 | 常见码 | 爬虫怎么处理 |
| --- | --- | --- | --- | --- |
| `2xx` | 成功 | 请求被正常处理 | `200 OK`、`201 已创建`、`204 无内容` | 正常解析 |
| `3xx` | 重定向 | 需要进一步操作 | `301 永久`、`302 临时`、`304 未修改` | requests 默认自动跟随，注意最终 URL |
| `4xx` | 客户端错误 | 你的请求有问题 | `400`、`401 未授权`、`403 禁止`、`404 不存在`、`418 彩蛋`、`429 太频繁` | 检查请求头、降速、换 IP |
| `5xx` | 服务端错误 | 服务器自己出问题 | `500 内部错误`、`502 网关错误`、`503 维护中` | 稍后重试，别猛冲 |

> **看到 403 别慌**——通常是请求头太「裸」（没有 User-Agent），服务器当机器人拦了。下一章用 `requests` 加请求头就能解决。
>
> **看到 429**（Too Many Requests）= 你爬太快了，服务器限流。加 `time.sleep` 降速即可（第 11 章详讲重试退避）。
>
> **看到 4xx 第一反应是「检查自己」，看到 5xx 第一反应是「等等再试」**——这个分寸感很重要。

## 六、请求头：你给服务器的「自我介绍」

请求头是一组键值对，告诉服务器「我是谁、我要什么格式、我从哪来」。爬虫最关心的几个：

| 请求头 | 作用 | 值示例 | 爬虫关注点 |
| --- | --- | --- | --- |
| `User-Agent` | 浏览器/客户端标识 | `Mozilla/5.0 (Windows NT 10.0...) Chrome/126.0` | 缺失或非浏览器 UA 常被 403 |
| `Cookie` | 登录态 / 会话标识 | `session_id=abc123` | 需要登录才能看的内容靠它 |
| `Referer` | 从哪个页面点过来的 | `https://example.com/list` | 部分防盗链站点会校验 |
| `Accept` | 期望的内容类型 | `text/html,application/json` | 影响返回格式 |
| `Accept-Language` | 想要的语言 | `zh-CN,zh;q=0.9` | 影响返回内容语种 |
| `Accept-Encoding` | 可接受的压缩方式 | `gzip, deflate, br` | 服务器据此压缩，requests 自动解压 |
| `Host` | 目标主机名 | `httpbin.org` | 通常自动填充，无需手动设 |

> **如何找真实请求头**？浏览器 F12 → Network → 点任意请求 → Headers → Request Headers，就能看到浏览器实际发的全部请求头。**照着抄是最快的学习方式**；把它存成字典，就是第三章的 `headers=` 参数。

## 七、常见的坑：重定向、403/404、乱码、缓存

| 现象 | 本质原因 | 排查 / 处理 |
| --- | --- | --- |
| `301/302` 重定向后拿到意外页面 | 服务器把请求转移到新地址（如 HTTP 跳 HTTPS、旧域名跳新域名） | requests 默认自动跟随，用 `resp.url` 看最终地址、`resp.history` 看跳转链 |
| 明明 URL 对却返回 `404` | 资源路径真的不存在，或需要特定参数/请求头才返回内容 | 先用浏览器打开同一 URL 对比；检查是否需要登录态/参数 |
| 返回 `403` 而不是 `404` | 服务器知道资源存在，但拒绝给你（UA 裸、无 Referer、IP 被拦） | 补 User-Agent、Referer 等请求头（第 3、11 章） |
| 中文乱码（如 `æ\x85...`） | 服务器声明的编码与实际字节不符，requests 猜错编码 | `resp.encoding = "utf-8"` 后再取 `resp.text`（第 3 章实操） |
| 改了页面却还是旧内容 | 浏览器/CDN 缓存了响应 | 加随机查询参数破缓存，或检查响应头 `Cache-Control` / `304 Not Modified` |
| `304 Not Modified` 但没有内容 | 请求带了 `If-None-Match` / `If-Modified-Since`，服务器说「你缓存里的是最新的」 | 爬虫一般不要带这两个头，去掉或换新会话 |

> **404 与 403 的区别值得记住**：404 = 「没有这个东西」，403 = 「有，但不给你看」。前者改 URL，后者改身份/频率。把它们混为一谈，会让你在错误的方向上浪费很多时间。

## 九、小结

- HTTP = 请求 → 响应。请求三要素：请求行（方法+URL+协议）、请求头、请求体；响应 = 状态行 + 响应头 + 响应体。
- URL 五段：协议 / 主机 / 路径 / 查询 / 片段（`#` 不发服务器）。
- `GET` 取、`POST` 交；参数一个在 URL、一个在请求体。
- 状态码：`2xx` 成功、`3xx` 重定向、`4xx` 多是被拦、`5xx` 可重试；`418` 是 HTTP 彩蛋。
- 请求头里 `User-Agent` / `Cookie` / `Referer` 是爬虫最常调的三个，用 F12 抄浏览器真实值。
- 排查心法：404 改 URL、403 改身份、乱码改编码、旧内容破缓存、重定向看 `resp.url`。
- 下一章用 `requests` 把这些概念变成代码——你会发现它正好对应本章的请求三要素与响应结构。
